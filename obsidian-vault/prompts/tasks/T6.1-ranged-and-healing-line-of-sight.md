## Reason for revision

T6 was implemented and reviewed against an agreed scope explicitly excluding line-of-sight checks. During review, the requester added obstacle blocking for both ranged attacks and targeted healing. This changes the accepted behavior and is a separate scope revision, rather than an unmet original T6 criterion. The original T6 requirements, implementation and verification record remain the review baseline.

## Objective

Reject a ranged attack or targeted heal when a blocking obstacle crosses the source-to-target path on the XZ ground plane, and explain the rejection through the existing debug action feedback.

## Requester decisions — 2026-10-20

- Use task T6.1, titled **Ranged and healing line of sight**.
- T6 cannot be accepted until T6.1 is resolved because this changes ranged attack behavior directly.
- Show line-of-sight failure only in debug action feedback. Do not add failed-action entries to combat history.
- Treat low and high obstacles identically. Ground-plane obstruction blocks even when a 3D line between unit centers would pass above or below the obstacle.
- Only active, enabled, solid 3D colliders under the existing scene hierarchy named `Obstacles` (including nested descendants) qualify. The requester referred to this as the “Obstacle” group; the existing scene/setup name is `Obstacles`.

## Scope changes

- Add a shared obstacle line-of-sight validation used by `CombatSystem.TryRangedAttack` and `CombatSystem.TryHeal`. Keep validation in combat ownership so it also applies to callers outside the debug UI.
- Use the XZ projections of the source/target positions and obstacle collider footprints. Obstacle height and the units' Y separation do not change blocking behavior. A collider behind the source or beyond the target does not block the segment.
- Resolve blockers from the configured `Obstacles` hierarchy rather than blocking every collider on the Default layer. Unit bodies, ground, and colliders outside that hierarchy do not block these actions. Ignore disabled colliders, inactive objects and trigger-only volumes.
- Preserve existing source/target, faction, death and range validation. For otherwise valid, in-range requests, line-of-sight failure rejects the action before health resolution or successful combat events.
- Expose the rejection reason to `CombatDebugActions` without duplicating obstacle checks in presentation. The ranged action still targets the boss; the heal action still targets Tank.
- Show exactly `Ranged DPS failed because of line of sight` or `Healer failed because of line of sight` in the existing debug status area for the respective blocked action. Treat this as normal feedback, not a Unity Console error.
- Blocked actions apply no damage/healing, emit no successful damage/healing/death event, append no combat history entry, and display no successful ranged tracer.
- Extend existing setup/arena-generation integration to configure the obstacle hierarchy reference while preserving existing scene customization and asset identities. Reapplying setup must not duplicate components, subscriptions or references.

## Acceptance criteria

1. An otherwise valid, in-range Ranged DPS-to-boss attack fails when an active solid collider under `Obstacles` crosses the XZ source-to-target segment.
2. An otherwise valid, in-range Healer-to-Tank heal fails under the same obstruction rule; Tank is injured so healing success/failure is observable.
3. Low and high blockers both reject each action, including a low blocker that a unit-center 3D ray would pass over. Moving the source/target so the XZ path clears the collider permits the action again.
4. Colliders nested under `Obstacles` block; colliders outside that hierarchy do not. Friendly/hostile unit bodies and the arena floor do not block sight. Disabled, inactive or trigger-only obstacle colliders do not block.
5. Obstacles behind the source or beyond the target do not reject a clear source-to-target segment.
6. Blocked ranged attacks show `Ranged DPS failed because of line of sight`; blocked heals show `Healer failed because of line of sight` through the existing debug feedback.
7. Each blocked action leaves health and combat history unchanged, emits no successful damage/healing/death outcome and shows no successful ranged tracer. Normal rejection creates no Unity Console error.
8. Clear ranged attacks and heals preserve configured amounts/range, death/faction checks, immediate resolution, effective outcome logging and reactive health updates. Existing invalid/dead/out-of-range feedback remains accurate.
9. Melee, direct debug damage, kill and reset behavior remain operational without the new line-of-sight restriction.
10. Selection/hotkeys, manual movement ownership, obstacle navigation and mutually passable units retain their T6 behavior.
11. Scene/setup references are applied and saved through Unity. Reapplying setup preserves the feature without duplicating components/subscriptions or replacing customized arena geometry.
12. Play-mode checks prove the game is advancing; the actual Game view shows the intended failure messages; compilation and the final Console have no introduced errors. Verification gaps, if any, are explicitly reported.

## Implementation and verification — 2026-10-20

The separately requested implementation is present in the saved arena. `CombatSystem` owns a shared `CombatLineOfSight` helper and a serialized reference to `Obstacles`. Ranged/healing overloads expose `CombatActionFailure.LineOfSight` while preserving the original boolean call sites. `CombatDebugActions` uses that result for the agreed messages. Rejected sight checks return before health resolution, event publication or tracer presentation. Existing combat log types/infrastructure are unchanged.

The helper uses actual 3D collider overlap/sweep queries, spanning qualifying obstacles vertically while following the XZ segment. This intentionally treats low/high/elevated cover identically and avoids blocking on an obstacle's empty axis-aligned bounding-box corners. A 0.001-unit query radius supplies a small geometric tolerance; transforms are synchronized per action. Only active, enabled, non-trigger colliders under the configured root count.
